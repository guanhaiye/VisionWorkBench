# 基于 YOLO11 的行为识别算法实施方案

## 1. 实施目标与首期范围

本实施方案用于指导团队从零搭建可运行、可训练、可部署、可验收的行为识别系统。

首期交付以下四种行为：

1. 区域闯入
2. 区域滞留
3. 人员聚集
4. 人员跌倒

第二期扩展：

- 打架与推搡
- 奔跑与追逐
- 抽烟与打电话
- 未佩戴安全帽等PPE违规
- 标准工序与违规操作

首期技术基线：

```text
Python 3.11
PyTorch
Ultralytics YOLO11s / YOLO11s-pose
ByteTrack
OpenCV + FFmpeg
FastAPI
Redis
PostgreSQL
ONNX Runtime（开发部署）
TensorRT FP16（生产优化）
```

## 2. 实施原则

- YOLO11负责目标和姿态感知，不直接承担所有行为分类。
- 越界、滞留和聚集使用可解释的轨迹规则。
- 跌倒使用几何候选、姿态时序模型和倒地持续状态联合判断。
- 所有报警均经过连续帧确认、状态机和冷却机制。
- 重型模型由候选事件触发，不对所有画面持续运行。
- 原始模型分数、融合原因和事件状态全部可追溯。
- 先完成端到端闭环，再使用现场数据逐步提高精度。

## 3. 系统组件

```text
摄像头/视频文件
      ↓
video-worker：解码、重连、抽帧、环形缓存
      ↓
inference-worker：YOLO11检测和YOLO11-Pose
      ↓
tracking-engine：ByteTrack及人员上下文
      ↓
behavior-engine：区域规则、姿态时序和动作模型
      ↓
event-engine：融合、状态机、去重、事件录像
      ↓
API/消息队列：查询、推送、配置和人工反馈
```

### 3.1 视频接入服务

职责：

- 接入RTSP、本地视频和测试图片序列
- 维护摄像头在线状态
- 网络断开后指数退避重连
- 统一帧时间戳
- 按推理配置抽帧
- 保存事件前10秒的环形缓存
- 检测黑屏、冻结、严重模糊等视频异常

每帧数据结构：

```python
FramePacket(
    camera_id: str,
    frame_id: int,
    timestamp_ms: int,
    image_bgr: np.ndarray,
    width: int,
    height: int,
)
```

### 3.2 推理服务

职责：

- 批量执行目标检测
- 按需执行人体姿态估计
- 统一模型输出格式
- 维护模型版本和设备分配
- 记录推理耗时

检测输出：

```python
Detection(
    class_id: int,
    class_name: str,
    confidence: float,
    bbox_xyxy: tuple[float, float, float, float],
)
```

姿态输出：

```python
PoseDetection(
    bbox_xyxy: tuple[float, float, float, float],
    confidence: float,
    keypoints: np.ndarray,  # [17, 3]，x/y/confidence
)
```

### 3.3 跟踪服务

每路摄像头使用独立跟踪器，避免不同摄像头ID相互污染。

人员上下文：

```python
TrackContext(
    camera_id: str,
    track_id: int,
    first_seen_ms: int,
    last_seen_ms: int,
    bbox_history: deque,
    footpoint_history: deque,
    keypoint_history: deque,
    speed_history: deque,
    zone_states: dict,
    event_states: dict,
)
```

默认参数起点：

```yaml
tracker:
  type: bytetrack
  track_high_thresh: 0.50
  track_low_thresh: 0.10
  new_track_thresh: 0.60
  track_buffer: 30
  match_thresh: 0.80
```

参数最终以现场验证集为准。

## 6. 首期算法实现

### 6.1 公共处理流程

每个有效视频帧执行：

```text
1. 读取帧并生成单调递增时间戳
2. YOLO11检测人员及业务物品
3. ByteTrack更新人员轨迹
4. 将Pose结果与人员轨迹匹配
5. 更新TrackContext历史缓存
6. 执行区域类行为规则
7. 对跌倒候选执行姿态时序识别
8. 更新事件状态机
9. 产生事件时保存证据并推送
10. 清理超时Track及缓存
```

系统内部所有持续时间基于时间戳计算，不能简单使用“帧数/FPS”，因为实时视频可能掉帧或动态抽帧。

### 6.2 区域闯入

位置点：

```python
foot_x = (x1 + x2) / 2
foot_y = y2
```

判断流程：

```text
人员脚点进入多边形
→ 状态变为SUSPECTED
→ 连续满足0.5秒
→ 状态变为ALARMED
→ 保存截图和事件录像
→ 人员离开区域持续1秒后RECOVERED
```

防抖要求：

- 多边形边缘设置内外两条迟滞边界，或使用进入/退出不同阈值。
- Track短暂丢失不立即判定离开。
- 同一Track在冷却时间内不重复报警。

### 6.3 区域滞留

为每个Track和Zone保存：

```text
entered_at
last_inside_at
accumulated_inside_ms
warning_sent
alarm_sent
```

短暂漏检小于2秒时继续累计；超过2秒时暂停或结束本次停留。具体阈值由现场遮挡情况调整。

### 6.4 人员聚集

每次规则运行时统计ROI内有效Track数，使用时间窗口平滑：

```text
smoothed_count = 最近2秒人数的中位数
```

中位数比单帧计数更能抵抗短时漏检。聚集事件以区域为主体，不绑定单一Track ID。

### 6.5 跌倒候选规则

从关键点计算：

- 肩部中心、髋部中心和踝部中心
- 肩髋向量与竖直方向夹角
- 人体框宽高比
- 髋部归一化下降速度
- 头部与髋部相对高度
- 可见关键点比例

关键点质量：

```text
pose_quality = confidence > 0.3的关键点数 / 17
```

`pose_quality < 0.5` 时不允许单独依赖姿态输出正式报警，应延长确认或触发RGB复核。

候选分数示例：

```text
candidate_score =
0.30 × 身体水平程度
+ 0.25 × 髋部下降速度
+ 0.20 × 人体框宽高比变化
+ 0.15 × 头部低位程度
+ 0.10 × 低位持续程度
```

候选分数达到0.55后，截取该Track最近2～3秒的关键点序列执行ST-GCN或PoseC3D。

### 6.6 姿态序列预处理

原始输入：`[T, 17, 3]`。

处理步骤：

1. 按时间戳重采样为固定长度，例如30帧。
2. 低置信度点标记为缺失。
3. 对短时缺失进行线性插值。
4. 使用左右髋中心作为坐标原点。
5. 使用肩宽或躯干长度做尺度归一化。
6. 保留关键点置信度掩码。
7. 计算速度和加速度作为可选附加特征。

不能使用整幅画面坐标直接训练，否则模型容易记忆摄像头位置而不是动作。

### 6.7 跌倒最终决策

```text
fall_score =
0.55 × pose_model_probability
+ 0.20 × horizontal_score
+ 0.15 × descent_score
+ 0.10 × lying_duration_score
```

正式报警条件：

```text
fall_score ≥ 0.75
AND 发生过快速下降或明显失衡
AND 低位状态持续 ≥ 1.5秒
AND pose_quality达到要求或RGB复核通过
```

坐下、弯腰、系鞋带、俯卧撑、躺床等必须作为困难负样本加入训练和测试。

## 7. 第二期算法实施

### 7.1 打架识别

触发候选的条件包括人员接近、轨迹碰撞、腕部高速运动和多人加速度异常。候选出现后，裁剪包含相关人员的联合区域，增加20%上下文边距，形成2～4秒视频片段。

首选X3D-S进行实时分类，输入16～32帧、224×224。类别至少包含：

```text
fight, push, hug, handshake, play, run, carry, normal_interaction
```

连续两个窗口超过阈值后报警，SlowFast或VideoMAE可作为服务端复核模型。

### 7.2 抽烟与打电话

先验证目标人物像素高度和手部可见性。低于可用条件时输出“不可可靠判断”，避免强制报警。

实现内容：

- 训练香烟、手机等小目标检测类
- 计算物品与嘴、耳、手腕的归一化距离
- 对人物上半身裁剪执行局部视频分类
- 使用持续时间和动作重复次数过滤误报

### 7.3 PPE与工序

PPE使用人物框内从属关系，不以全局最近距离简单匹配。工序使用有限状态机，每个步骤保存开始、结束和证据帧；非法状态跳转产生违规事件。

### 8.2 标注规范

检测标注：

- 框住完整可见目标。
- 遮挡目标仍保留合理的可见/完整框规则，且全数据集一致。
- 不把反光、屏幕画面和海报中的人物标为真实人员。
- 小于业务可识别尺寸的目标单独标记或排除。

行为片段标注：

- 记录动作开始、关键时刻和结束时间。
- 标记参与人物ID。
- 保留动作前后至少1秒上下文。
- 对模糊样本标记为`uncertain`，不强制归入正负类。
- 每个正样本配套收集相似负样本。

### 8.3 数据质量检查

自动检查：

- 空标注和越界框
- 重复帧与重复视频
- 视频损坏
- 类别分布异常
- 训练集与测试集近重复
- 同一摄像头/同一事件泄漏

抽取至少10%的数据进行人工复核，核心测试集建议双人交叉复核。

## 9. 训练与模型管理

### 9.1 检测模型训练流程

```text
数据检查
→ COCO预训练权重初始化
→ 训练YOLO11s
→ 验证集调参
→ 独立摄像头测试
→ 导出ONNX
→ ONNX结果一致性检查
→ 性能压测
→ 注册模型版本
```

建议保留以下模型元数据：

```json
{
  "model_name": "person_ppe_detector",
  "version": "1.0.0",
  "architecture": "yolo11s",
  "input_size": 960,
  "classes": ["person", "helmet", "phone"],
  "dataset_version": "2026-08-22",
  "metrics": {"map50": 0.91, "recall": 0.88},
  "sha256": "..."
}
```

### 9.2 姿态行为训练流程

```text
运行Pose模型提取关键点
→ 保存关键点及置信度
→ 固定长度重采样
→ 训练ST-GCN基线
→ 按摄像头划分验证
→ 分析混淆矩阵
→ 增加困难负样本
→ 导出ONNX
→ 集成状态机验证
```

### 9.3 模型发布规则

新模型必须满足：

- 独立测试集核心指标不低于当前生产版本。
- 每路每日误报数不恶化至业务阈值之外。
- 推理延迟和显存符合预算。
- ONNX/TensorRT输出与PyTorch输出在容差内一致。
- 支持快速回滚到上一个模型版本。

## 11. 事件证据与隐私

- 环形缓存默认只在内存中保留。
- 只有正式事件才落盘保存证据。
- 设置事件录像自动过期时间。
- API按角色控制实时画面、录像和导出权限。
- RTSP密码、数据库密码和令牌不得写入仓库。
- 日志不得输出完整RTSP地址或隐私凭据。
- 按项目要求对非关注人员或人脸进行脱敏。
- 记录事件查看、下载和删除审计日志。

- API和WebSocket事件一致

### 12.3 视频回归测试

建立固定回归视频集：

```text
tests/videos/positive

tests/videos/night

```

- 单路连续运行72小时

- GPU显存是否持续增长
- CPU、内存、解码队列和推理队列积压
- 磁盘空间不足和存储服务异常

## 13. 验收标准

### 13.1 功能验收

- 摄像头可新增、停用和重连。
- 可配置归一化多边形区域。
- 实时显示检测框、Track ID、行为状态和置信度。
- 事件包含截图、前后录像、人员ID和触发原因。
- 支持事件检索、人工确认和误报反馈。
- 模型、配置和阈值均有版本记录。

### 13.2 算法验收

| 项目 | 首期目标 |
|---|---:|
| 闯入事件Recall | ≥95% |
| 滞留事件Recall | ≥95% |
| 聚集事件Recall | ≥90% |
| 跌倒事件Recall | ≥90% |
| 跌倒事件Precision | ≥85% |
| 简单规则事件延迟 | ≤1秒 |
| 跌倒报警延迟 | 1～3秒 |

必须同时约定每路摄像头每日允许误报数。仅用Recall验收会导致系统通过降低阈值获得高召回但产生大量误报。

### 13.3 性能验收

- 指定硬件和路数下推理队列无持续积压。
- 95分位端到端延迟满足业务指标。
- 连续运行无显存和内存持续泄漏。
- 单路断开不影响其他摄像头。
- 服务重启后配置、事件和模型版本可恢复。

## 14. 分阶段排期建议

以下为单个小型团队的参考排期，实际时间取决于现场数据和人员配置。

### 第1周：工程底座

- 创建项目结构和配置系统
- 接入本地视频与RTSP
- 集成YOLO11和ByteTrack
- 建立TrackContext
- 完成基本可视化和运行指标

### 第2周：区域行为闭环

- 截图、录像和事件API

### 第3周：跌倒规则基线

- 接入YOLO11-Pose

- 跌倒候选规则
- 采集并整理跌倒及困难负样本
- 建立事件级评估工具

### 第4～5周：跌倒时序模型

- 构建关键点数据集
- 训练ST-GCN或PoseC3D
- 融合模型与状态机
- 误报分析和阈值调优
- ONNX导出

### 第6周：部署与验收

- ONNX Runtime/TensorRT集成

- 断流恢复和稳定性测试

- 现场验收和问题清单

打架、抽烟等第二期行为应分别安排数据采集、模型训练和现场验收周期，不宜与首期同时承诺精度。

## 16. 上线流程

```text
离线开发与单元测试
→ 固定视频回归
→ 现场影子运行（只记录不报警）
→ 人工复核误报和漏报
→ 调整阈值并补充数据
→ 小范围启用低风险报警
→ 观察一至两周
→ 分批扩大摄像头范围
→ 建立月度或按需模型迭代
```

高风险场景中，首版报警建议由人工复核后处置，不能让算法结果直接触发不可逆的自动控制动作。

## 17. 主要风险与处理

| 风险 | 处理方案 |
|---|---|
| 人体过小 | 提高分辨率、调整摄像头或限制适用距离 |
| 遮挡导致ID切换 | 调整ByteTrack、增加ReID或使用区域级事件 |
| 夜间性能下降 | 夜间专项数据、补光或红外适配 |
| 跌倒误报较多 | 加入坐下、弯腰、躺卧等困难负样本和持续确认 |
| 打架误报 | 使用多人联合裁剪、姿态交互和连续窗口确认 |
| 多路视频算力不足 | 动态抽帧、批处理、候选触发和TensorRT |
| 现场域偏移 | 摄像头级测试、主动学习和增量训练 |
| 阈值难以统一 | 按摄像头、区域和事件类型分别配置 |
| 商业许可风险 | 上线前核对YOLO实现及所有依赖的许可证 |

## 18. 开工顺序

实际开发按以下顺序执行：

1. 创建项目骨架、配置系统和统一数据结构。
2. 打通本地视频到YOLO11检测及结果可视化。
3. 接入ByteTrack并验证人员ID稳定性。
4. 实现归一化ROI、闯入、滞留和聚集。
5. 实现通用事件状态机和事件证据录像。
6. 接入YOLO11-Pose和关键点序列缓存。
7. 完成跌倒几何规则基线及回归测试集。
8. 采集现场数据，训练ST-GCN/PoseC3D。
9. 完成融合、阈值优化和事件级评估。
10. 导出ONNX/TensorRT并进行多路压测。
11. 影子运行，收集误报、漏报并迭代。
12. 验收后分批上线。

本方案的第一技术里程碑不是“训练出一个模型”，而是完成一条可回放、可评估、可解释的端到端事件链路。只有事件链路稳定后，新增行为模型才具备持续迭代价值。
